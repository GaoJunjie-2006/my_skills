# 优质睡眠好帮手（sleep-helper）

把一个需要长时间自主执行的任务，在动手前拆解到"问无可问"，冻结成一份可无人值守执行的任务书，并在执行中设置超时与熔断。目标是让开发者在睡醒后直接拿到结果，而不是中途被叫起来做决策，或发现 agent 卡死。

## 0. 四条铁律（全程适用，任何步骤都不得违背）

这四条与下面的流程同等重要，优先级高于"图省事"。每做一步都拿它们对一遍。

**铁律 1：一切文字输出必须用中文。**
用户是中国人，看不懂英文。凡是要给人看的文字，一律中文，包括但不限于：与用户的对话、`任务书.md`、`技术说明书.md`、代码注释、提交信息（commit message）、日志说明、报错解释、最终交付说明。
唯一例外：代码本身的标识符（变量名、函数名、类名、文件名）按编程惯例用英文，不强行翻成中文拼音；但它们旁边的注释必须是中文。

**铁律 2：所有操作只在 git 的 develop 分支上进行，禁止碰 main。**
- 动手前先确认当前目录是不是 git 仓库；不是就先 `git init`。
- 然后切到 `develop`：`git checkout develop`；若该分支不存在，则从当前分支创建 `git checkout -b develop`。
- 全程只在 `develop` 上修改、提交、运行。**禁止在 `main` / `master` 上做任何修改或提交**；一旦发现自己在 `main` / `master` 上，先切到 `develop` 再干活。
- 每完成一个阶段就提交一次，提交信息用中文。
- 除非用户明确要求，否则不要自行把 `develop` 合并回 `main`、也不要 `git push` 到主分支。

**铁律 3：任务完成后必须产出技术说明书。**
跑完不等于交付完。任务结束（无论成功还是失败）都必须生成一份 `技术说明书.md`，把接口、函数规范、API 等讲清楚，供以后查阅。详见第 5 步。

**铁律 4：树状深挖必须分到"分无可分"为止。**
分支层数不固定、上不封顶，不许因为"已经分了几层"就停下。详见第 1 步。

触发后按下面五步走；每一步的产出都是下一步的输入。

## 1. 树状深挖：出框架 → 逐层细化 → 刨根问底

动手写任何代码、执行任何命令之前，先把任务建构成一棵由浅入深的决策树。

- **第一步，出大框架**：用一句话写出最粗的闭环。例如 "MCU 控制 boost 输出固定电压" 的大框架是：ADC 读取 → PID 计算 → MCU 输出占空比 → 再次采样 → 循环。
- **第二步，逐层细化**：对框架里每个节点追问"怎么做 / 用什么方式"。例如 ADC 用 DMA 还是软件直接读？PWM 频率取多少才能兼顾纹波与效率？PID 用增量式还是绝对式？
- **第三步及以后，继续下钻**：采样频率多少合适？ADC 用多少 cycles？怎么滤波？DMA 双缓冲还是单缓冲？PID 要不要限幅？主要靠 P 还是 I？……
- 如此往复，直到每个叶子节点都是一条无需再决策、可直接执行的明确指令，即"问无可问"。

**关于"画树状图"的硬性要求（深度上不封顶，必须分到分无可分）**

"画树状图"不是画个三四层的示意图交差，而是把整件事真正拆穿。具体要求：

- **起点是每一个大方向**：第 1 层列出的每个大模块 / 大环节，各自都是一棵独立的子树，各自从头往下分。有几个大方向，就有几棵树，一棵都不能少。
- **层数不固定、上不封顶**：不同分支的深度可以完全不同——浅的两三层，深的十几层都很正常。**不存在"分到第 N 层就够了"这种规则**，禁止因为"已经分了三四层""差不多得了"而停止下钻。
- **唯一停止条件是"分无可分"**：每个叶子节点都必须是一条原子指令——能直接翻译成一行代码、一条命令、一个参数值或一个具体文件路径。只要脑子里还冒出"这个到底该怎么定？""这里选哪个？"，就说明没分到底，必须继续往下分。**分到再也问不出新问题为止，才算这棵树画完了。**
- **不许偏科**：不能只把感兴趣的那一条分支挖穿、其余分支一笔带过。每个大方向都要独立地分到"分无可分"。
- **注意"分支"的两种含义**，两种都要一路分到底：
  1. **技术路线的分叉**：A 方案 / B 方案怎么选（例：DMA 还是软件读？venv 还是 conda？）；
  2. **结构上的拆分**：模块 → 子模块 → 函数 → 参数 → 取值（例：滤波模块 → 滑动平均 → 窗口长度取多少）。
- **落笔形式**：把树完整写进 `任务书.md` 的第 3 节，逐层展开、标清层级，让读者能一眼看出从大方向到原子指令的完整路径。

**每一层都遵循"最少人工摩擦"原则**：凡是有多条技术路线的地方，优先选不需要人工操作的那条——
- 不需要下载/安装额外软件、不需要 GUI、不需要人工点选的方案优先（例：前端用 HTML/Web+JS，而非必须装 Visual Studio 才能跑的方案）。
- 现成环境优先于新建环境（例：已有 venv 直接用，不重造）。
- CLI / 脚本化 / 无头优先于图形界面交互。
- 常见、成熟的方案优先于冷门方案，减少意外。

**何时问用户**：只有当某个决策确实无法凭上述原则或常识自行定夺（如需要账号、真实硬件参数、明确偏好）时，才停下来向用户提问，并把答案记入任务书。目标是"一次问完"，不让同一类问题在执行中途反复出现。

## 2. 卡点预判：把"会卡住"的地方提前想清楚

深挖的同时，标记任务里所有"可能长时间阻塞或死循环"的操作——编译、安装依赖、下载、启动服务、跑测试、连设备等。

对每个这样的操作，在执行前写清楚三件事：
- **预期耗时**：正常应该多久出结果。
- **超时阈值**：超过多久仍无结果就判定异常。
- **判定与应对**：超时后先看日志，区分三种情况——
  1. 终端真卡死 / 进程挂了 → 停止，排查代码或重跑；
  2. 模型精度不足导致的"无意义循环"（反复做同一件事无进展）→ 换策略，不重复同一动作；
  3. 实际在正常运行、只是偏慢 → 继续等。

**熔断规则**：同一操作连续失败或空转超过 N 次（默认 3 次）仍无进展时，必须换一条路，禁止原样重试。为所有长操作保留日志，供超时后判断用。

## 3. 冻结任务书：生成 任务书.md

把前两步的结论冻结成一份格式严谨的 `任务书.md`。它是后续执行的唯一依据，也是"醒来有结果"的保障。

- 按下面「任务书模板」的骨架逐段填写。
- 任务书必须包含：目标与成功判据、完整决策树（每个大方向各自下钻、逐层"选什么、为什么"、直到分无可分）、所有已解决的人工决策点及其答案、每个卡点操作的超时阈值与熔断规则、明确禁止中途询问用户的事项清单、**语言与分支约定（中文 + develop 分支）**、**交付物清单（含 `技术说明书.md`）**。
- 措辞面向 AI 执行者：指令式、无歧义、可机械执行，不含"视情况""酌情"等留白。

生成后按用户习惯作为目标交给执行（如 `/goal 任务书.md`）；若无该命令，则直接依据任务书逐条执行。

## 4. 执行与守夜

依据任务书开始执行。执行期间：
- **开工第一件事：切分支。** 确认已在 git 仓库的 `develop` 分支上（见铁律 2）；不在 `develop` 上就不许动手。
- 对每个标记过的操作启用超时与熔断（见第 2 步）。
- 出现任务书未覆盖的新情况时，优先用任务书里的原则自行解决；确实需要人的决定，才唤醒用户。
- 定期落盘中间结果，并阶段性提交到 `develop`（提交信息用中文），避免长时间运行后一次崩溃前功尽弃。
- 执行过程中产生的一切文字（日志、报告、给用户的说明）都用中文。

## 5. 收尾交付：技术说明书 + 结果说明

跑完不等于交付完。任务结束后（无论成功、部分成功还是失败）都要交出下面两样东西，**缺了 `技术说明书.md` 视为任务未完成**。

**（1）技术说明书.md（必须生成）**

把本次任务产出的所有技术资产写成一份可长期查阅的中文文档，与任务书放在同一目录，命名 `技术说明书.md`，至少覆盖以下内容：

- **总览**：这个项目 / 这套代码是干什么的，整体结构长什么样（文件树 + 每个文件一句话说明）。
- **接口清单**：所有对外暴露的东西逐个列出——函数 / 方法 / HTTP 端点 / CLI 命令 / 配置项，写清名称、作用、所在文件与行号。
- **函数规范**：逐个函数写清——
  - 签名与所在位置；
  - 入参：名称、类型、含义、取值范围、是否可选、默认值；
  - 返回值：类型与含义；
  - 副作用：是否读写文件、发网络请求、改全局状态；
  - 异常 / 错误处理：什么情况会抛错、抛什么、调用方怎么处理；
  - 调用前置条件与注意事项。
- **API 说明**（若有）：HTTP 方法、路径、请求参数与请求体示例、响应体示例、状态码与错误码表、鉴权方式。
- **数据结构**：核心结构体 / 类 / 数据库表 / JSON schema 的字段定义与含义。
- **依赖与环境**：运行时与版本、第三方库及版本、环境变量、安装与启动步骤。
- **调用示例**：每个接口给一段可直接复制运行的最小示例（含预期输出）。
- **变更记录**：本次新增 / 修改了哪些文件，各自做了什么改动。
- **已知限制与后续可改进点**。

写作要求：全部中文；面向"三个月后已经忘了细节的自己"来写，务求拿来就能用；不确定的地方不要编，标注"未验证"。

**（2）完成 / 失败说明**

- 完成时：交付了什么、成果放在哪个路径、怎么验证（附可复现的验证命令或步骤）、怎么运行。
- 失败时：卡在哪一步、报错日志、已尝试过哪些应对、下一手建议怎么走。

最终目标：开发者在运行期间无需干预，睡醒后直接拿到可用结果、一份中文的 `技术说明书.md`，以及一份清晰的完成 / 失败说明。

## 树状深挖示例

三个完整示例，用于校准下钻方式与"最少人工摩擦"原则。

> **注意**：下面的示例为了行文简洁，只写到第 4 层左右，**这不是深度上限，只是示例的截断**。实际执行时，每个大方向都要一直分到"分无可分"为止，层数不固定、上不封顶。

**示例 1：MCU 控制 boost 输出固定电压**
- 第 1 层（大框架）：ADC 读取 → PID 计算 → MCU 输出占空比 → 再次采样 → 循环。
- 第 2 层（细化）：ADC 用 DMA 还是软件直接读？PWM 频率多少才能兼顾纹波与效率？PID 增量式还是绝对式？
- 第 3 层（深化）：ADC 采样频率多少？用多少 cycles？怎么滤波？DMA 双缓冲还是单缓冲？PID 要不要限幅？主要靠 P 还是 I？
- 第 4 层（刨根问底）：滤波用滑动平均还是卡尔曼？要不要低通？ADC 采样周期会不会和 PID 计算周期重叠冲突？
- ……如此往复，直到每个叶子都能直接写成一条 C 代码指令。

**示例 2：环境选择（venv vs conda）**
- 用现成的还是新建？→ 优先现成。
- 若需新建：venv 还是 conda？→ 已装哪个用哪个，都没装则用 venv（更轻、无额外安装）。
- pip 包没有怎么办？→ 先看有无离线 / 内置替代，再考虑下载；下载要有超时与镜像回退。

**示例 3：前端实现（VS vs HTML vs Web+JS）**
- 用什么做前端？Visual Studio / 原生 HTML / Web+JS？
- 按"最少人工摩擦"：HTML/Web+JS 不需要额外安装软件、可直接产出，更适合 AI 自主开发；Visual Studio 需要安装与 GUI 操作，优先级最低。
- 结论：默认 HTML/Web+JS；除非用户明确要求桌面原生。
