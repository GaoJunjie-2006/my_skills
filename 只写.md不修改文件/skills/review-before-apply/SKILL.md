# Review Before Apply — 先审阅再修改

## 核心原则

当用户请求对代码或文件进行任何变更时，**不要直接修改任何文件**。禁止使用 `Edit`、`Write` 等工具直接变更用户文件。而是创建一个 `.md` 文件，在其中详细说明需要做出哪些修改、如何修改以及为什么这样修改。

## 输出文件规范

### 文件名

根据修改内容创建一个描述性的文件名，格式为：`<修改主题>-修改说明.md`

例如：
- `修复登录bug-修改说明.md`
- `添加用户导出功能-修改说明.md`
- `重构数据验证逻辑-修改说明.md`

### 文件内容结构

使用以下模板来组织内容：

```markdown
# [修改标题]

## 概述
用 2-3 句话说明这次修改的目的是什么，解决什么问题。

---

## 修改清单

### [序号]. `文件路径`

**修改位置**：`行号范围`（或具体函数/代码块名称）

**修改前**：
```[语言]
修改前的代码片段
```

**修改后**：
```[语言]
修改后的代码片段
```

**说明**：解释为什么要这样改，解决了什么问题，有什么注意事项。

---

## 执行步骤

按顺序列出用户需要执行的操作：

1. 打开 `文件路径`，定位到第 X 行
2. 将选中的代码替换为...
3. ...
```

### 内容要求

- **修改前后对比**：每个修改都要同时展示"修改前"和"修改后"的代码
- **位置明确**：精确到文件名 + 行号范围 或 函数名称，让用户能快速定位
- **解释原因**：说明为什么这样改，而不只是"把A改成B"。解释背后的逻辑
- **循序渐进**：按合理的顺序排列修改项，让用户可以一步步跟着做

## 触发规则

### 默认行为（必须触发）

**任何请求都默认触发此技能**，包括但不限于：

- 修改代码文件
- 添加新功能
- 修复 bug
- 重构代码
- 优化性能
- 更改配置
- 更新文档
- 添加注释
- 回答涉及代码实现的问题（即使没有明确要求修改）
- 分析代码并提供改进建议
- 任何会产生代码或文件输出的场景

判断标准：**只要用户的请求可能涉及代码变更或文件操作，就触发。如果有疑问，默认触发。**

### 唯一例外

只有当用户明确说了 **"直接输出代码"** 时，才不触发此技能，改为正常直接输出或修改文件。

## 注意事项

- 可以创建新文件（.md 说明文件）来说明修改方案，但不能直接修改用户的代码文件
- 如果用户说"直接帮我改"等类似表述但没有说"直接输出代码"这个精确短语，仍然要触发此技能
- 回答纯概念性问题（不涉及代码）时不需要触发
